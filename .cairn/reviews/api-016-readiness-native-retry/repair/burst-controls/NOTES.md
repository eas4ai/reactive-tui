# Prepared portable burst transport (not applied)

Primary XNU source defines TTYHOG=1024 and its noncanonical PTY writer limits the input queue at TTYHOG-2. With IO_NDELAY it returns a partial write, or EWOULDBLOCK if no progress occurred. Sources: https://raw.githubusercontent.com/apple-oss-distributions/xnu/main/bsd/sys/tty.h (171-173) and https://raw.githubusercontent.com/apple-oss-distributions/xnu/main/bsd/kern/tty_dev.c (874-905). This source evidence supports handling a smaller queue; it is not the pending CI observation.

The prepared portable-burst.patch changes only the burst producer/fixture and native-wrapper success wording. Linux still requires precisely 2048 bytes accepted by its single initial write before releasing the consumer. It never adds a second Linux tty write and rejects short initial writes. Other Unix hosts inspect the actual initial write count, release an atomic record naming that count, and send any remainder with bounded nonblocking writable polling. Total required delivery remains 2048 on every host; exhausted polling and terminal restoration remain mandatory. Both producer logs and terminal captures distinguish fully-queued from streamed delivery. The Rust consumer also asserts that Linux received a fully queued 2048-byte announcement. The three dependency readiness tests and their mechanism command are untouched.

run-probe.py passed four controls through real Linux PTYs, using a deliberate 511-byte short-write adapter to model a legal transport result: original rejects short write; corrected simulated Darwin handles short writes and EAGAIN and delivers all 2048; corrected Linux uses one 2048-byte write before release; corrected Linux still rejects 511. The Python consumer tests transport/barrier behavior, not Crossterm or macOS. These controls do not replace the native Rust fixture or all-platform UnixStream readiness tests. Every probe subprocess has a five-second deadline with kill/reap cleanup; logs, PTY captures and write histories are retained.
