DECISION

Question:   May keyframe sampling and untyped conversion require an explicit value trait, so custom value types must define their interpolation and conversion?
Recommend:  Require an explicit keyframe value trait and provide implementations for built-in numeric, color, transform, CSS, tuple and discrete values. Keep the existing constructor and sampling names where possible; add checked conversion with a named property for multi-property keyframes. Custom types implement the trait instead of receiving guessed values.
Because:    Two public API tests compile and fail: typed f32 0 to 10 samples as 0 at halfway, and untyped x=4 converts to 0. The direct API currently requires only Clone, or Clone plus Default for conversion. Neither bound supplies interpolation or a way to recover a typed value. The commitment also requires preserving working public APIs and escalating conflicting contracts.
If wrong:   Existing callers that use their own Clone types will stop compiling at keyframe sampling or conversion until they implement the value trait. Built-in callers retain their call shape and gain correct values. No runtime repair has been implemented; the two regression tests intentionally remain failing.
Instead:    Preserve the current unrestricted generic methods and add separate interpolating and checked-conversion methods. That avoids the custom-type source break, but leaves the old numeric sampling and default-substitution paths defective; accepting that alternative requires explicitly revising API-013 rather than claiming it is repaired.
