Question:   May Props keep caller-invoked validate(), require named per-field rules, and require optional fields to be written as Option<T>?
Recommend:  Yes. Implement #[prop(validate = rule)], reject bare or malformed validation annotations, and keep the existing derive and builders.
Because:    Current validate always returns true and has no rules to enforce. Plain optional String fails; Option<String> works. Derive macros cannot rewrite input fields ([Rust Reference](https://doc.rust-lang.org/stable/reference/procedural-macros.html)). The proposal and compiler probes are in .cairn/reviews/api-018-props-contract.
If wrong:   Callers can construct invalid props until they call validate(); existing bare validation annotations must be migrated to named rules.
Instead:    Retain the broader automatic-validation/type-rewriting promise and design a macro/runtime API that can implement it.
